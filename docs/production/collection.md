## TL;DR

给前四回加一层**不打断阅读**的收集层：

| 问题 | 方案 | 代价 |
| --- | --- | --- |
| 现在只能顺着读，读完就没了 | **明信片册**：22 张地图 = 22 张卡 | 美术：22 张新图 |
| 地图上有很多地方剧情没走到 | **探索**：可自由走到的锚点变成「可寻访」，走到即开图鉴条目 | 需要一套自由移动模式 |
| 收集要有目标 | **册页拼合**：同属一组的卡拼成一页《金陵十二钗》式的册页 | 需设计组规则 |
| 不想变成打卡游戏 | **不做体力、不做签到、不做抽卡** | 零 |

**核心判断：卡片的主角不是「物品」，是「地点」。**

理由是数据上的：仓库里已经有 **22 张 40×40 等距地图、202 个锚点、59 个地名标签、134 张运行时素材**，而道具在《红楼梦》前四回里几乎不存在（只有那块石头和那块玉）。已有的资产和已有的地图，天然就是卡片的内容。反过来做道具卡，要新画几十张没人见过的器物。

## 二、核心循环

```
                    ┌──────────────────────────────────────┐
                    │                                      │
      读剧情  ──→  人物走到新地方  ──→  该地点的「见闻」入库  ──→  册页拼合
         ↑                                                      │
         │                                                      ↓
         └────────────  册页解锁新章节 / 新地点可寻访  ←──  收藏册
```

三件事，缺一不可：

1. **读** — 现有主循环，不变。
2. **到** — 地图上存在一些「剧情没安排、但人在那里」的地方。把这些做成可寻访点。
3. **集** — 到过的地方变成卡；集齐一组，拼出册页。

**关键设计决定：收集的触发是「到过」，不是「点击」。**

这样收集和阅读是同一条时间线上的两件事，而不是并行的两条任务系统。读者读第三回时走过大观园的一角，册子里就多一张；读第四回再走过，就再拼一页。

## 三、卡片系统

### 3.1 卡片的三个种类

只做三种，多了就不叫收藏了。

#### 甲 · 地志卡（明信片）

**内容**：一个地点。画面是那座地方的等距小景，题名是地名，下方一行原文引句或改编短句。

- 数量：**22 张**（每张地图一张），后续新回每加一张地图就加一张。
- 解锁：**读到该地图上的任何一段剧情**即解锁。不需要专门跑过去。
- 价值：低门槛、零打扰，是册子的底子。

> 为什么每张地图只给一张明信片？因为 22 张地图就是 22 个地点，再细分的收益很低，而美术成本是线性增长的。一张图讲一个地方，是最诚实的比例。

#### 乙 · 见闻卡（名物）

**内容**：一个人物、一件信物、一句话。

- 数量：首期 **约 40 张**，上限 60。
- 解锁：**读到一个特定节点**，或**寻访到一个特定锚点**。
- 三种来源：
  - **人物卡**（约 20 张）：如「衔玉而生的宝玉」「三万六千五百零一块的石头」「冷子兴」。卡面是立绘（已有 38 套）+ 一句原文。
  - **信物卡**（约 8 张）：如通灵宝玉、那块顽石、题诗的桃花笺（原文提及的）、/functions 的护官符。卡面是**已有素材**或**道具图形**（矢量绘制，不用 AI 画）。
  - **金句卡**（约 12 张）：如「好了歌」「护官符」「千里之外寄相思」类。卡面是**竖排文字 + 印章**，纯文字排版，零美术成本。

> 金句卡是这个方案里性价比最高的一类：不需要新画任何东西，只需要从 `docs/chapter0N-source.txt` 里取原文，配上已有的印章/纹样风格。

#### 丙 · 册页卡（拼图页）

**内容**：一组同类卡拼成的一页，带一段总题。

- 数量：首期 **4 页**。
- 例：
  - 《荣国府诸人》→ 需要「entry」地志卡 + 贾母/凤姐/宝玉/黛玉/探春/惜春/迎春/李纨/王夫人/邢夫人/薛宝钗/史湘云 共 13 张
  - 《甄家旧影》→ 甄士隐 / 甄英莲 / 封氏 / 娇杏 / 封肃 / 霍启 + 甄宅、姑苏、大如州 地志卡
  - 《宁荣谱系》→ 冷子兴演说里的门第名单
  - 《护官符》→ 四大家族的四段符 + 英莲身世

**解锁规则**：**卡片收集 + 剧情进度双条件**。例如「护官符」册页需要：4 张符卡已集 + 读到 C04-057（判案密室）。这让册页不只是收集的终点，而是**指向剧情的入口**。

### 3.2 卡片的字段

一张卡片就是一条数据。建议放 `design/collection-cards.json`：

```jsonc
{
  "id": "place.entry",
  "kind": "place",            // place | person | token | line | page
  "book": 3,                  // 首次出现的回目；册页卡可为 null
  "name": "荣国府 · 贾母院",
  "subtitle": "西门直进，穿堂插屏，至正房",
  "art": "place/entry",        // 指向卡面图；金句卡为 null
  "quote": "……",
  "source": {
    "node": "N005",           // 解锁节点
    "paragraphLead": "林黛玉扶著婆子的手"
  },
  "unlock": {
    "type": "read",            // read | visit | read_and_visit
    "node": "N005",
    "anchor": null             // visit 型用 "entry/flower_gate"
  },
  "group": "rongguo.people",   // 册页归属
  "order": 3
}
```

`unlock.type` 只有三种，引擎实现因此很薄：

| type | 触发条件 | 例子 |
| --- | --- | --- |
| `read` | 读过某节点 | 人物卡 |
| `visit` | 自由寻访过某锚点 | 隐藏地点 |
| `read_and_visit` | 两者都要 | 册页卡 |

### 3.3 解锁判定放在哪

**不放引擎里。** 引擎（`src/engine.ts`）目前只管剧情与演出，不该知道「卡片」。

新增 `src/collection.ts`，一个纯函数模块：

```ts
export function unlockedCards(
  readLog: string[],       // 引擎已有的 readLog，跨跳转保留
  visited: Set<string>,    // 自由寻访记录，形如 "entry/flower_gate"
  cards: Card[]
): Set<string>
```

它**只读**引擎的两个现成事实：

- `engine.readLog` —— 已读节点 id。上一轮刚做完的「回看不因跳转截断」正好提供了这个。
- `visited` —— 一个新的 `localStorage` 集合（见第四节）。

这样卡片系统是引擎的一层旁挂，不侵入 `StoryState`，不需要升存档版本号。

> 存档兼容性检查：`restore()` 里对 `state.readLog` 的校验已经是可选字段（`state.readLog !== undefined` 才校验），旧存档没有它也不报错。`visited` 完全独立于存档，单独存 localStorage。

## 四、探索：自由寻访

### 4.1 为什么需要它

32 个锚点从没被剧情走过。如果只做「读到就解锁」，这些地方就永远进不了册子，「探索」就是空话。

但**自由行走会和现有演出打架**：现在地图是纯观看的，镜头永远跟着人物走，没有玩家控制。

所以探索要有**明确边界**。

### 4.2 建议的边界：只在「行迹图」上移动

第三、四回用的是「荣国府总览」地图（`WorldMap.tsx`），它已经是一张可点击的平面图，12 个地点（10 个府内 + 2 个府外）。第一、二回用的是「本回行迹」地图（`JourneyMap.tsx`）。

**方案：探索挂在行迹图/总览图上，而不是等距舞台里。**

理由：

1. 等距舞台里做自由行走要重写镜头跟随、碰撞、寻路，是最大的风险面；
2. 行迹图已经是「地点之间的移动」，语义上正是「赶路」；
3. 现成的 `travelRoute` / `routePoints` / `alongRoute` 已经把两点之间的路径画出来了，探索只需要在这条路上加「停靠点」。

**具体做法**：在总览图/行迹图上，除了现有的 9–10 个「剧情地点」，再标出若干「可寻访点」。读者点一个可寻访点，播放一段短演出（一两句对白或纯文字），就解锁了对应的见闻卡。

### 4.3 哪些地方可以做可寻访点

候选池是那 32 个未走到的锚点 + 已走过锚点上的支线点。逐张评估：

| 地图 | 可寻访点 | 为什么合适 | 风险 |
| --- | --- | --- | --- |
| `entry` 荣国府 | `passage_entry` 穿堂入口、`screen_detour` 插屏绕行、`courtyard_west` 西院 | 黛玉入府的实际路线，读者会想知道绕屏风走是什么样 | 低 |
| `east` 贾赦东院 | `small_court` 小院、`bamboo_door` 竹门、`xing_room` 邢夫人正房 | 原文写「恐怕不便」，不去反而更对；可做成「只见院门，不入」的记录 | 中（会与「设计推定」冲突） |
| `guowai` 郭外 | `temple_path` 寺道、`dusk_field` 暮色田野 | 第二回「出城」一路，可补一段行路 | 低 |
| `night` 碧纱橱 | `letter_place` 书信处 | 次日省晨写信，与剧情呼应 | 低 |
| `canal` 运河 | `bank_near/mid/far` 岸、`reed_bend` 芦苇弯 | 舟行途中本来就停靠 | 低 |
| `central` 荣禧堂 | `east_court` 东院 | 第四回接风时走过 | 低 |
| `myth/dream/ruins/tavern` | `left/right/rear` | **通用脚手架，不是真地点** | **不做** |

**结论：首期做 12–14 个可寻访点**，分布在 6 张地图上，全部是已有锚点，不需要新增地图数据。

### 4.4 一处需要读者注意的边界

「可寻访」必须**不制造原文没有的事实**。

`east` 那个例子就很危险：原文说黛玉「恐不便」，只命婆子打点，不进。做成「可寻访邢夫人正房」就是把设计推定升格成了正文，违反 AGENTS.md 里「原文明示、人物转述、设计推定分开记录」这条。

**规则：可寻访点只能记录「观察」，不能记录「经历」。** 卡片上写的是「远远望见竹门紧闭，婆子传话便回」，不是「进屋拜见」。

## 五、册页拼合

### 5.1 为什么要有册页

只有卡片没有册页，收集就只是集邮，没有「完成感」。

册页提供**目标感**：读者看着册子上还差的那几个名字，会想去补。

### 5.2 册页的四页

| 册页 | 需要的卡 | 数量 | 剧情门槛 |
| --- | --- | --- | --- |
| 《荣国府诸人》 | 12 人物卡 | 13 | 读到第三回末（N 系列） |
| 《甄家旧影》 | 6 人物 + 3 地志 | 9 | 无（第一、二回即可） |
| 《宁荣谱系》 | 门第卡 8 张 | 8 | 读到 C2-026（宁荣两位国公的家谱） |
| 《护官符》 | 4 符卡 + 2 见闻 | 6 | 读到 C04-057（判案定谳） |

四页的难度是递进的：第一页纯收集，第二页要回看第一、二回，第三页要找到冷子兴讲家谱的那几段（`C2-023`–`C2-026`），第四页要一路读到第四回的密室。

### 5.3 册页解锁的奖励

不要给数值奖励（这个游戏没有战斗，没有数值）。给**内容**：

- 册页解锁后，在「原文与改编」面板里多一段**未收录原文**——即现在因为篇幅没放进正文的那部分红楼梦原文。这是最对味的奖励：读者集齐了「护官符」册页，就得到完整的护官符原文。

这是这个方案里我最满意的一点：**收集的奖励是原书本身**。它把「收集」和「读原著」绑在一起，而不是把「收集」变成游戏化装饰。

## 六、界面

### 6.1 放在哪

顶部导航已经比较满（回目选择、进度、自动/暂停、回看、静音、设置）。**不再加顶部按钮。**

方案：把「地图地点」面板（现有 `atlas`，22 张地图列表）升级为**册页**，在里面加一个「见闻」标签页。也就是：

```
设置 → 地图地点   →  改名「册页」，两个标签：地图 / 见闻
```

不新增入口，不改导航结构，符合 AGENTS.md「只保留一条紧凑顶部导航」。

### 6.2 册页的视觉

沿用现有的「人物图鉴」（`cast-gallery`）样式：网格卡片、点开看详情。卡片本身：

```
┌─────────────────┐
│                 │  ← 卡面图（地志/人物/纹样）
│    [ 卡面 ]      │     128×160 或 160×200
│                 │
├─────────────────┤
│ 荣国府 · 贾母院   │  ← 题名
│ 「西门直进……」   │  ← 副题或引句
└─────────────────┘
```

- 未解锁：卡面显示**墨色剪影 + 问号**，不显示名字。
- 已解锁：正常显示。
- 册页卡：单独一格，显示拼合进度「8 / 13」。

### 6.3 卡面美术从哪来

这是**最大的成本项**，必须说清楚。

| 卡片类型 | 数量 | 卡面来源 | 新美术量 |
| --- | --- | --- | --- |
| 地志卡 | 22 | **从等距地图里截取**——用现有 `project()` 投影把地图裁一块出来 | 0（程序化生成） |
| 人物卡 | 20 | 已有立绘（`cast` 的 38 套）裁切 | 0 |
| 信物卡 | 8 | **矢量绘制**（通灵宝玉、顽石、护官符、桃花笺…） | 少量 SVG |
| 金句卡 | 12 | 纯排版：竖排文字 + 印章底纹 | 0 |
| 册页卡 | 4 | 纹样拼贴（可复用已有 UI 纹样） | 少量 |

**地志卡的程序化生成是这套设计的关键技巧。**

现有地图是 Phaser 画的，没有离屏快照。但 `MapScene` 已经有完整的绘制流程，可以在 `preload` 之后、正式渲染之前，先用一份离屏 `Graphics` 把该地图画一遍（`create()` 里那段地板绘制逻辑可以抽成一个 `paintFloor(g, map)`），然后 `generateTexture()` 成一张 `RenderTexture`，裁出中央区域当卡面。

**好处**：卡片与地图永远一致，改了地图卡面自动跟着变；**不需要任何新美术**。

**代价**：要动 `MapScene.ts` 的绘制结构（把地板绘制抽成可复用的函数），有回归风险。

**替代方案（更稳）**：不截图，而是在地图加载完后用 Playwright 跑一次批处理，人工截 22 张图存到 `public/assets/cards/`。一次性成本低，但以后改地图要手动重截。

**建议**：先用替代方案把功能跑通，视觉满意后再考虑程序化。

### 6.4 收集进度条

顶部进度条现在显示「前四回剧情进度」。可以在它旁边加一个很小的册页完成度（比如一个小图标 + `7/50`），但**不加第二根进度条**。

## 七、数据模型与文件

### 7.1 新增文件

```
design/collection-cards.json    # 卡片定义（数据）
src/collection.ts               # 解锁判定（纯函数，无副作用）
src/CollectionPanel.tsx         # 册页面板 UI
public/assets/cards/            # 卡面图（若采用人工截图方案）
```

### 7.2 存储

| 数据 | 位置 | 理由 |
| --- | --- | --- |
| 卡片定义 | `design/collection-cards.json` | 属于内容，与 story/sections 同级，走 `check_content.mjs` 校验 |
| 已解锁卡片 id | `localStorage['honglou.collection.v1']` | 派生数据，可从 readLog 重算 |
| 已寻访锚点 | `localStorage['honglou.collection.visited.v1']` | 独立于剧情存档 |
| 册页完成 | 同解锁集合，可实时算 | 不用单独存 |

**已解锁卡片是派生数据**，理论上可以完全从 `readLog` + `visited` 重算。之所以还要存，是因为 `readLog` 存在**剧情存档**里，而读者可能换了存档重读；单独存一份解锁记录，语义更清楚：**「我在这部书里见过什么」比「我读到了第几个字」更像收藏**。

### 7.3 与现有校验的关系

`scripts/check_content.mjs` 现在会检查：story 节点有原文证据、地图被引用、theme 有配曲、文档被链接。加入卡片后要加三项：

1. 每张卡的 `source.node` 必须是一个真实存在的 story 节点 id；
2. 每张卡的 `unlock.anchor` 必须是一个真实存在的锚点（形如 `sceneId/anchorName`）；
3. 每张卡必须被至少一个册页引用，或显式标记为「散卡」。

**不要**给卡片加新的 `check_content` 硬失败项在第一期——新系统上线时如果 22 张地志卡有一张锚点写错，会让整个内容校验挂掉。**先 WARN 后 FAIL**。

## 八、分期

### 第 0 期 · 骨架（不产出任何美术）

- `design/collection-cards.json`：只写 22 张地志卡 + 4 张册页卡
- `src/collection.ts`：解锁判定
- `src/CollectionPanel.tsx`：网格 + 已解锁/未解锁两态
- 册页面板挂进现有的「地图地点」面板
- 存档不升版本（解锁集独立存）

**验收**：读完第三回，册子里出现 13 张「荣国府诸人」相关的卡；用 `localStorage` 手工注入后刷新，状态保持。

### 第 1 期 · 见闻与寻访

- 补 40 张见闻卡（金句卡优先，零美术）
- 12–14 个可寻访点接到总览图/行迹图
- 寻访演出：一次短过场 + 解锁卡片
- 册页解锁奖励：原文摘录进「原文与改编」

**验收**：从行迹图走到一个可寻访点，卡片解锁，册页进度条 +1；跳回原来的剧情位置，演出状态不受影响。

### 第 2 期 · 卡面与打磨

- 22 张地志卡卡面（截图或程序化）
- 人物卡裁切
- 册页拼合动效

### 不做（明确划界）

- **不做**抽卡、掉落、随机、概率
- **不做**体力值、签到、每日任务
- **不做**数值养成（等级、属性、战力）——这个游戏是阅读，不是有战斗的游戏
- **不做**成就弹窗打断阅读——解锁反馈只在册页面板里可见，顶部不弹

> 这一条很重要。一个在读小说时突然弹出「恭喜解锁新卡！」的界面，是对阅读的干扰。**收集的反馈应该在玩家主动去看的时候给**，不在演出过程中给。

## 九、风险与待决

| # | 风险 | 影响 | 建议 |
| --- | --- | --- | --- |
| 1 | 地志卡卡面用截图 → 改地图要重截 | 中 | 先人工截图跑通，程序化作为后续优化 |

| 4 | 「可寻访」把设计推定升格成正文 | **高** | 硬规则：只记录观察，不记录经历；每张卡标注 `classification: explicit \| design` |
| 5 | 22 张卡 × 每张都要引句 → 引句校对量 | 中 | 金句卡必须逐字核对 `docs/chapter0N-source.txt`；改编短句标 `adaptation` |

| 7 | 读者会想「集卡」而跳过剧情 | 中 | 地志卡只靠读剧情解锁，没有捷径；寻访点也不给剧情内容 |

### 待你决定的三件事

1. **卡面要不要程序化生成？** 我倾向第一期人工截图（快、稳），第二期再改程序化。
2. **金句卡算不算「卡片」？** 它是纯文字牌。要不要归入同一个册子，还是单开一个「摘录」页？
3. **要不要「未解锁也能看名字」的预览？** 我倾向**不给**——未解锁就是未知，看到了会毁掉收集的期待。但这条是口味问题。
